## Q2. disconnectAll: синхронность, мёртвые процессы, пусто, идемпотентность

Код `mcp-adapter.ts:345-358`:
```ts
async disconnectAll(): Promise<void> {
  for (const [name, entry] of this.servers.entries()) {
    if (entry.process) {
      try { entry.process.kill(); console.log(`[MCP] Disconnected from ${name}`); }
      catch (e) { console.warn(`[MCP] Error disconnecting ${name}:`, e); }
    }
  }
  this.tools.clear();
  this.initialized = false;
}
```

1. **Синхронность: ПОДТВЕРЖДЕНО** — в теле нет ни одного `await`; цикл `for..of` с `kill()` внутри
   исполняется целиком синхронно в момент вызова (`async` — только для сигнатуры Promise).
   Следствие для fix: `void mcpAdapter.disconnectAll()` шлёт все kill до возврата управления.
2. **Уже упавший процесс:** обработчик `child.on('exit')` (`mcp-adapter.ts:111-115`) **заменяет**
   запись сервера на `{ config, initialized: false }` — без `process`. Тогда `if (entry.process)`
   (347) скипает сервер. Если exit ещё не успел прийти — `kill()` вызывается; `ChildProcess.kill()`
   возвращает `false`, когда сигнал отправить нельзя (мёртвый процесс), а любые броски глотает
   `try/catch` (348-353) с warn.
3. **Пустой `servers`:** цикл — 0 итераций; `tools.clear()` на пустой Map и `initialized = false`
   безопасны; Promise резолвится. Ничего не бросает.
4. **Идемпотентность: ПОДТВЕРЖДЕНА (практическая)** — повторный вызов безвреден: tools уже очищены,
   `initialized` уже false; для процессов: если exit успел — скипаются (п.2), если нет — kill
   повторно (`false`/throw проглатывается). **Эдж:** `entry.process` вручную не обнуляется —
   `getStatus()` (`mcp-adapter.ts:363-370`) может показать `connected: true` для убитого сервера
   до прихода события `exit`. На корректность quit не влияет; кандидат на hardening (см. FIX-SPEC §4).

## Q3. Порядок в before-quit: ДО или ПОСЛЕ closeMemory

Текущий хендлер (`main.ts:976-985`, top-level, синхронный):
`stopProactiveEngine → stopBackgroundMonitor → stopLifeLoop → stopVramGate → stopReminderChecker →
stopTelegramBot → closeMemory() → globalShortcut.unregisterAll()`.

Кто из оставшегося кода может дёрнуть MCP-запрос в момент quit:
- `memory/manager.ts:159` — `remember()` → `retainToGraph` → `mcpAdapter.callTool('memory_add'…)`;
- `memory/manager.ts:353` — `flushL2()` (внутри `maintenance()`, триггерится IPC
  `memory:maintenance`, `main.ts:805-815`);
- `tool-loop.ts:284` — `l2Search()` при recall (только во время активного диалога).

**Решение: подтверждаю дефолт «ПОСЛЕ `closeMemory()`, перед `unregisterAll`».** Обоснование:
1. К моменту `closeMemory()` все источники новых MCP-вызовов уже остановлены (движки — 977-981,
   telegram — 982); остаться могут только in-flight вызовы.
2. `closeMemory()` (`memory/store.ts`: `walCheckpoint(); db.close(); db = null`) — **синхронная**;
   весь хендлер — один синхронный блок, поэтому резолвы in-flight промисов физически не могут
   выполниться «между» строками 983 и 984. Технически оба порядка эквивалентны по гонке с БД,
   но kill MCP **после** БД-флаша семантически правильнее: сначала закрываем локальные данные,
   затем рвём внешние процессы, затем локальные подписки (shortcut).
3. Обратный порядок (kill до `closeMemory`) рубил бы MCP-транспорт, пока БД ещё жива — не даёт
   выигрыша, а успешный ответ обрываемого вызова не должен успеть записать provenance после
   закрытия БД (`manager.ts:160-162`, `355` — `setFactProvenance` пишет в SQLite; отказы MCP
   глотаются: `manager.ts:226-229`).
4. `unregisterAll` — чисто локальный UI-teardown; MCP-вызов ставим **перед** ним, чтобы внешние
   ресурсы закрывались до локальных (единый стиль teardown).
Путь quit: tray «Выход» (`main.ts:196-200`, `app.quit()`) и `quitAndInstall` autoupdater'а —
оба эмитят `before-quit`; `window-all-closed` не выходит (972-974, U.N.A. остаётся в tray) — MCP
намеренно живёт вместе с приложением.


## Q4. Тестируемость: стратегия

`before-quit`-хендлер в vitest напрямую не вызвать (это коллбек на объекте Electron `app`,

**Уровень 1 — unit-тесты `disconnectAll` (новый файл `tests/ai/mcp-disconnect.test.ts`):**

  (через `queueMicrotask`) эмитит ответ в `stdout` тем же `id` — тогда `connectAll()` проходит
  handshake и `tools/list` без реальных процессов и без 15-30с таймаутов `waitForResponse`
  (`mcp-adapter.ts:217, 265`).
- Кейсы (фиксируют текущую семантику, P1-2):
  1. `new MCPAdapter().disconnectAll()` на пустом наборе → resolve, без throw;
  2. 2 сервера (enabled) + `connectAll` → `getToolDefinitions().length > 0` → `disconnectAll` →

  3. повторный `connectAll` после `disconnectAll` снова наполняет tools (нет мёртвой блокировки);

  6. эмуляция события `exit` у фейка → запись сервера сбрасывается (111-115) → следующий
     `disconnectAll` kill НЕ вызывает (skip по `entry.process`);
  7. сервер `enabled: false` → `connectAll` скипает (72), `disconnectAll` kill не вызывает.
- **Прецедент уже есть:** `tests/safety/indirect-injection.test.ts:293-317` — тот же
  `MCPAdapter` с реальным child; он остаётся integration-проверкой «kill реального процесса
  по disconnectAll в finally». Новый файл дополняет его мок-юнитами (быстрыми и без процессов).
- Запреты: реальные `spawn`, сеть — не нужны: всё через фейк.

## Q5. Риски фикса

1. **Async без await в синхронном хендлере.** Не риск: тело `disconnectAll` синхронно (Q2.1),
   `void`-вызов отправляет все kill-сигналы до возврата из хендлера. Electron не успеет выйти
   раньше, чем ядро получит kill. Ожидание завершения процессов не требуется: ОС добьёт
   TerminateProcess'ом асинхронно, stdio-трубы закрываются при выходе родителя.
2. **Windows-специфика kill.** `ChildProcess.kill()` на Windows = `TerminateProcess` (без graceful
   SIGTERM): процесс умирает мгновенно. Для Graphiti-сервера с собственной БД (`una-graph.kz`) это
   может означать незавершённый write — но до фикса процесс переживал выход вообще (зомби):
   нетто-улучшение. Дерево процессов (`python` → его внуки) `kill()` НЕ гасит — вне scope
   минимального фикса; при необходимости отдельная задача на `taskkill /T /F` (Windows-only ветка).
3. **Зависшие stdio-трубы.** Если процесс не отреагирует на kill (редко), трубы закроются при
   выходе родителя; зависший ребёнок останется один — тот же класс F15, но случаи kill-неудачи
   глотаются с warn (351-353), т.е. не хуже текущего состояния.
4. **Повторный вызов/идемпотентность.** Подтверждена (Q2.4); double-quit не ломает.
5. **Порядок с closeMemory.** Гонок нет: весь хендлер синхронный (Q3.2); выбран «после» (Q3).
6. **HTTP-серверы** (`transport: 'http'`, mcp-adapter.ts:119-122) процесса не имеют —
   `disconnectAll` для них no-op; соединений нет по дизайну.
