## 1. Findings (Что обнаружено)

1. **F-кандидат (parseGoalToken, create):** regex `/^\[GOAL\]\s+create:\s*(.+)\s*\|?\s*(.+)$/` —
   `|` в `\|?` необязателен, поэтому жадная группа `(.+)` съедает всё, кроме последнего символа:
   - `'[GOAL] create: do X | a, b, c'` → `description='do X | a, b,'`, `subgoals=['c']`
     (шаги уходят в description, последний символ становится единственным subgoal);
   - `'[GOAL] create: do X'` (без pipe) → `description='do'`, `subgoals=['X']`
     (теряется последний токен описания).
   Итог: LLM-команда `[GOAL] create:` практически всегда создаёт искажённую цель. Зафиксировано
   тестами «как есть» (P1-2), код не тронут. Решение — Архитектору (нужен нежадный `(.+?)` +
   обязательный pipe или split по первому `|`).
2. **Эдж (не дефект):** `updateSubgoalStatus` при пустых subgoals — index 0 не проходит
   bounds-check (`0 >= 0`) → silent no-op; NaN-progress (`0/0`) недостижим через публичный API.
3. **Эдж (поведение):** `resumeGoal` не-interrupted цели — UPDATE no-op по `WHERE status='interrupted'`,
   но функция всё равно возвращает Goal со статусом «как есть» (snapshot не сбрасывается).
4. `progress` в БД — REAL (не INTEGER), NaN не связывался бы, но см. п.2 — ветка недостижима.
