# Безопасность U.N.A.

## Философия

U.N.A. **осторожна по умолчанию**. Лучше задать лишний вопрос, чем удалить данные.

## Уровни риска команд

В `electron/safety/classifier.ts` определены 4 уровня:

### `safe` — выполняется без вопросов

Примеры: `ls`, `cat`, `pwd`, `ps`, `whoami`, `df`, `free`, `dir`, `echo`, `git status`, `npm list`

### `caution` — U.N.A. предупреждает, но выполняет

Примеры: `wget`, `curl`, `git push`, `cp -r`, `chmod -R`

U.N.A. скажет «Загружаю файл из интернета, это может быть небезопасно» и продолжит.

### `dangerous` — требует подтверждения через диалог

Категории:
- **Удаление:** `rm -rf`, `rmdir`, `del`, `unlink`
- **Привилегии:** `sudo`, `runas`
- **Установка ПО:** `apt install`, `yum install`, `pip install`, `npm install -g`
- **Сеть/файрвол:** `iptables`, `netsh`, `route`
- **Процессы:** `kill`, `killall`, `taskkill`
- **Диск:** `fdisk`, `diskpart`, `format`
- **Реестр:** `reg add`, `reg delete`
- **Сервисы:** `systemctl stop`, `service restart`
- **Системные пути:** `/etc/`, `C:\Windows`, `/usr/`, `/bin/`, `System32`

При такой команде U.N.A.:
1. НЕ выполняет её
2. Показывает диалог с описанием риска
3. Жмёт «Подтвердить» или «Отклонить»

### `forbidden` — блокируется ВСЕГДА

Никогда не выполняется, даже с подтверждением:

| Паттерн | Причина |
|---------|---------|
| `rm -rf /` | Удаление корневой ФС |
| `rm -rf *` | Удаление всех файлов в текущей папке |
| `mkfs.*` | Форматирование ФС |
| `dd if=... of=/dev/...` | Прямая запись в блочное устройство |
| `:(){ :\|:& };:` | Fork bomb |
| `shutdown`, `reboot`, `halt`, `poweroff` | Выключение/перезагрузка |
| `> /dev/sda` | Запись в жёсткий диск |
| `chmod -R 777 /` | Открытие прав на корень |
| `init 0` | Выключение через init |

U.N.A. скажет «Эта команда заблокирована. Альтернатива: ...» и предложит безопасный вариант.

## Защищённые файлы

Некоторые файлы U.N.A. **никогда не читает** и не показывает содержимое:

| Паттерн | Что это |
|---------|---------|
| `.env`, `.env.local`, `.env.production` | Переменные окружения с секретами |
| `id_rsa`, `id_ecdsa`, `id_ed25519` | SSH приватные ключи |
| `*.pem`, `*.key` | SSL/TLS ключи |
| `*.pfx`, `*.p12` | Сертификаты с приватным ключом |
| `/etc/shadow`, `/etc/passwd` | Системные пароли |
| `credentials`, `credentials.json` | Файлы кредов (gcloud, AWS) |
| `.kube/config` | Kubernetes конфиг с токенами |
| `.npmrc`, `.pypirc` | Конфиги с токенами пакетных менеджеров |
| `.git-credentials` | Git креды |
| `.aws/credentials` | AWS ключи |
| `*seed*`, `*mnemonic*` | Seed фразы криптокошельков |

При попытке прочитать — U.N.A. вернёт ошибку «файл защищён» и не покажет содержимое.

## Подтверждение через токены

Чтобы LLM не мог «обойти» подтверждение повторным вызовом, используется механизм токенов:

1. LLM вызывает `execute_command({ command: "rm -rf /tmp/*" })`
2. Safety classifier определяет: `dangerous`
3. Генерируется уникальный токен: `exec_<timestamp>_<hash>`
4. Команда НЕ выполняется
5. U.N.A. возвращает LLM: `needs_confirmation: { token, action, risk, details }`
6. LLM формирует ответ для пользователя
7. Пользователь нажимает «Подтвердить»
8. Токен сохраняется в `electron-store` (переживает перезапуск)
9. LLM снова вызывает `execute_command` — теперь токен валиден, команда выполняется

```typescript
// В tools/index.ts
if (safety.level === 'dangerous') {
  const token = `exec_${Date.now()}_${Buffer.from(cmd).toString('base64url').slice(0, 12)}`;
  if (!ctx.confirmedTokens.has(token)) {
    return { success: false, needs_confirmation: { token, action, risk, details } };
  }
}
```

## Изоляция процессов

**Renderer (React)** работает в песочнице Electron:
- Нет прямого доступа к Node.js API (`fs`, `child_process`)
- Только методы, экспортированные через `preload.ts` → `window.una`
- Даже если в ответе LLM будет XSS — он не получит доступ к системе

**Main process (Node.js)** имеет полный доступ, но:
- Каждый IPC-хендлер валидирует аргументы
- Опасные операции проходят через safety classifier
- Требуется подтверждение пользователя

## Что U.N.A. НЕ делает

- Не отправляет ваши файлы в облако без явной команды
- Не сохраняет пароли, ключи, токены в память
- Не выполняет команды от имени администратора без sudo/runas (это потребует отдельного подтверждения)
- Не открывает внешние ссылки без вашего ведома (только через `shell.openExternal`)
- Не обновляет сама себя автоматически (только через electron-updater с подписью)

## Журналирование

Все вызовы инструментов сохраняются в **episodic memory** (SQLite):
- Что вызвано
- С какими аргументами
- Какой результат
- Когда

Можно посмотреть в панели «Память» → история диалогов.

## Аудит безопасности

Если вы хотите проверить, что U.N.A. делала:

1. Откройте SQLite БД:
   ```bash
   sqlite3 "%APPDATA%\una-assistant\una-memory.db"
   ```
2. Посмотрите последние команды:
   ```sql
   SELECT timestamp, role, content FROM messages
   WHERE content LIKE '%execute_command%'
   ORDER BY timestamp DESC LIMIT 50;
   ```

## Ограничения

- U.N.A. не защищает от social engineering — если вы сами подтверждаете опасную команду, она выполнится
- Safety classifier основан на regex — хитрая обфускация команды может обойти (но это редкость)
- Локальный LLM может галлюцинировать и вызывать странные инструменты — всегда проверяйте tool_calls в UI

## Если что-то пошло не так

1. **Случайно подтвердили опасную команду:**
   - Немедленно остановите U.N.A. (Ctrl+C в терминале или убейте процесс)
   - Проверьте, что именно выполнилось — посмотрите в `messages` таблицу
   - При необходимости — восстановите из бэкапа

2. **U.N.A. удалила важный файл:**
   - Проверьте корзину (rm без -f обычно спрашивает)
   - Используйте `extundelete` (Linux) или recuva (Windows)
   - Включите более строгий режим — только `safe` команды, без `dangerous`

3. **Появилось подозрение на взлом:**
   - U.N.A. работает локально, без удалённого доступа
   - Проверьте, не установлен ли вредоносный Ollama (модели могут быть заражены)
   - Смените все пароли, если в чате упоминались `.env`, ключи
